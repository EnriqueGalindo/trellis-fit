A 35B mixture-of-experts model in 8.5 GiB on Apple Silicon

Enrique Galindo

We took a 2.08-bit EXL3 quant of Qwen3.6-35B-A3B, removed the 26 least-used experts from every layer and stored the embedding table in 8 bits. The result is 8.46 GiB on disk and peaks at 10.19 GiB at 8k context. Against the full-precision model on 336 AppWorld task-runs it scores 67.9% to 72.6%.

Summary

  • Size. 10.57 GiB to 8.46 GiB with no re-quantization. Kept tensors are copied byte for byte.
  • Distribution cost. Mean KL divergence against bf16 goes from 0.1141 to 0.1264. Top-1 agreement stays at 85.5%.
  • Coding. On HumanEval the pruned quant matches bf16 at 159 of 164, where the unpruned quant scores 132. The unpruned quant gets stuck redrafting inside its reasoning; the pruned one almost never does. We cannot explain that yet.
  • Agent work. On AppWorld the pruned model trails bf16 by about 5 points pooled over two rounds. The first round, taken alone, showed no gap, and that was an artifact of a reply limit that held the full model back.
  • Harness. Qwen3.6's chat template drops earlier thinking unless preserve_thinking is set. Sending thinking back in the request is not enough.

What we built

The starting point is UnstableLlama's 2.08 bpw EXL3 of Qwen3.6-35B-A3B: 40 layers, 256 experts per layer, 8 routed per token. The target is a 16 GB Mac mini, which leaves roughly 10.5 GiB for weights once the system and a working context are accounted for.

  1. Count expert use. We ran the bf16 model over the WikiText-2 training split plus a sample of code and counted how often the router picked each expert in each layer.
  2. Remove the 26 least-used experts per layer. Every layer keeps its 230 most-used experts, renumbered. The router matrix keeps the matching rows and num_experts is lowered. The vision tower is removed.
  3. Store embeddings in 8 bits. EXL3 leaves the 248,320 × 2,048 embedding table at 16 bits. We store int8 codes with one 16-bit scale per row and expand only the rows a lookup touches. Relative error is 0.85%.

KL rank is not task rank

The source quant has the best KL of the three quants and the worst HumanEval score. Its failures are almost all one kind: the model redrafts its answer inside the reasoning block until the token limit. The full-precision model never does this. Sampling at temperature 1.0 halves it (31 to 15) and a repetition penalty does not help. The pruned quant, built from the same weights minus 10% of the experts, nearly stops doing it. One untested guess is that the rarely used experts are also the worst-quantized ones.

The 6-problem gap between the two pruned variants is borderline on its own (7 against 1 discordant problems, p ≈ 0.07) and no other test repeats it.

  • Round one flattered the quant. The 8,192-token limit cut off 125 of the full model's 2,500 replies and 12 of the pruned model's 2,885. The full model passed 64% of the tasks where it was cut off and 80% of the rest.
  • Round two is the fairer comparison. Cut-offs fell to 2 and 0. The pruned model took more steps (20.0 against 16.6 per task) and ran out of steps on 7 tasks, all failed; the full model ran out on 2.
  • Run-to-run noise is large. The same model on the same tasks flipped 36 results between rounds for bf16 and 50 for the pruned model. One run cannot resolve a difference of fewer than about 10 tasks.

Two things the harness taught us

Thinking sent back is not thinking rendered

Qwen3.6's chat template renders an earlier turn's reasoning only when preserve_thinking is true, or for turns after the last user message. In a ReAct loop every step follows a user message, so without the flag all earlier reasoning is dropped at render time, whatever the client sends. The same 39-message conversation renders to 37,918 prompt tokens with the flag and 9,656 without. The template has no reasoning_effort variable at all.

Empty thinking blocks teach the model not to think

MLXL3 sets preserve_thinking unconditionally. When the client does not send thinking back, every earlier assistant turn is rendered with an empty thinking block. AppWorld's prompt contains ten example assistant turns, and the model copied them: median reasoning fell to 178 characters per step and 27% of replies never closed the thinking block. With the history rendered the same way as mlx-lm, median reasoning returned to about 1,200 characters.

Engine

EXL3 on Apple Silicon runs in MLXL3, a Rust engine on MLX. Our fork adds four small changes on top of commit 1d0a519f: loading the 8-bit embedding tensors, passing reasoning_content through to the template, a switch for the thinking-history behaviour above, and accepting an empty tool_calls field. Draft decoding (DFlash, MTP) was off throughout.

Generation speed is 108 to 124 tokens per second in a short test and the same for all three quants. Under sustained AppWorld load the server slowed to about 40 tokens per second within ten minutes and further over hours; restarting it restored the speed. We have not found the cause.

Limits

  • One unseeded run per AppWorld cell. MLXL3 rejects seed, top_p and min_p, so runs are not paired by seed and the sampler is top-k only.
  • Nothing has been run on a 16 GB machine yet. Memory figures come from a 128 GB Mac.
  • Experts were ranked by use on WikiText-2 training text and code. Other workloads may lean on the removed experts.
  • MMLU and the long-context tests were not run on bf16, and the pruned model without 8-bit embeddings was not run on AppWorld.
  • The effect of pruning on thinking loops is an observation on one model at one bit rate. We have not tested other pruning levels.
  • Text only, and untested in exllamav3 on NVIDIA or AMD.

Reproduce

  • Models: pruned10-q8emb (needs the fork) and pruned10 (stock MLXL3). Each carries pruning.json with the original index of every kept expert.
  • pruned10 runs in stock MLXL3 with no build step: mlxl3 serve <model> --context-length 65536.
  • pruned10-q8emb does not load in stock MLXL3. It needs the fork built from source (Rust 1.89 or later, Python 3.12, MLX 0.32.2); the model card lists the exact commands.
  • Both paths were checked on 2026-11-25 from a fresh download of each model and a fresh clone of the fork.
  • The pruning and 8-bit conversion scripts are not published yet, so the models can be run but not rebuilt from this note.
  • Both models and the base are Apache 2.0. MLXL3 is MIT.
